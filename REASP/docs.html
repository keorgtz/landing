Que es REASP?

REASP (Ryou Adaptive SDD System) es un framework de Sub-Agent Driven Development (SDD) disenado especificamente para OpenCode Go. Es el primer "Sistema Operativo de Desarrollo IA Adaptativo" que ajusta dinamicamente su flujo de trabajo segun la complejidad de cada tarea.

A diferencia de los asistentes de IA tradicionales que usan un unico modelo y un flujo fijo, REASP implementa un sistema de 7 agentes especializados coordinados por un orchestrator, cada uno con el modelo de IA optimo para su funcion especifica.

La caracteristica distintiva de REASP es su sistema de ModeProfiles: 8 configuraciones predefinidas que determinan cuantas fases SDD se ejecutan y que agentes participan. Una tarea simple como un CRUD usa 3 fases (Fast), mientras que un sistema enterprise usa 8 fases completas (Enterprise).

Filosofia

REASP no es solo una herramienta. Es una filosofia de desarrollo con tres principios fundamentales:

1. "Conceptos > Codigo"

El valor no esta en la cantidad de codigo generado, sino en la calidad de los conceptos y decisiones de arquitectura. REASP prioriza el diseno correcto sobre la implementacion rapida.

2. "El humano siempre lidera"

Los agentes de REASP son herramientas, no reemplazos. El desarrollador humano toma las decisiones finales, aprueba los cambios y dirige la estrategia. La IA se adapta al humano, no al reves.

3. "El modelo correcto, para la tarea correcta"

El problema hoy no es "tener una IA". Es usar el modelo correcto, con el flujo correcto, para la tarea correcta. REASP resuelve esto con model routing inteligente y pipelines adaptativos.

text 
# Principios de diseno de REASP
- Sin agentes recursivos (evita bucles infinitos)
- Sin especificaciones masivas para tareas triviales
- Adaptacion real: simple = 3 fases, complejo = 8 fases
- Contexto eficiente: solo los agentes necesarios participan
- Transparencia total: cada decision es visible y auditable

Instalacion Global

La instalacion global instala REASP como un plugin del sistema de OpenCode, disponible para todos los proyectos.

Paso 1: Clonar el repositorio

bash 
git clone https://github.com/keorgtz/REASP.git

Paso 2: Ejecutar el instalador TUI

bash 
cd REASP/installer
npm install
node index.js

Paso 3: Seleccionar configuracion

El TUI installer te guiara a traves de:

  1. Seleccion del ModeProfile por defecto (recomendado: RyouSet)
  2. Activacion de agentes (todos activados por defecto)
  3. Configuracion de rutas y directorios
  4. Verificacion de conectividad con modelos de IA

Paso 4: Verificar instalacion

bash 
/rass-setup

Este comando muestra el estado actual de REASP, incluyendo el ModeProfile activo y la configuracion de agentes.

Instalacion Local

Para instalar REASP solo en un proyecto especifico (sin afectar la configuracion global):

bash 
cd tu-proyecto
git clone https://github.com/keorgtz/REASP.git .rass
node .rass/installer/index.js --local

La instalacion local crea la estructura .opencode/ dentro del proyecto actual sin modificar la configuracion global de OpenCode.

Desinstalacion

Para remover REASP completamente del sistema:

bash 
node REASP/installer/index.js --uninstall

Esto eliminara:

  • Los plugins de OpenCode (plugin.js, tui.js, rass-core.js)
  • Los directorios agents/, rules/, sdd-profiles/, phases/
  • El estado de runtime (conservando backups en runtime/backup/)

Para desinstalacion local, simplemente elimina el directorio .opencode/ del proyecto.

ModeProfiles

Los ModeProfiles son el corazon de REASP. Definen que fases SDD se ejecutan, que agentes participan y que modelo de IA se usa en cada fase.

Un ModeProfile es un archivo JSON que especifica:

  • name — Nombre identificador del perfil
  • phases — Array ordenado de fases a ejecutar
  • effort — Nivel de esfuerzo: low, medium, high, extreme
  • model_strategy — single (un modelo para todo) o per-phase (modelo por fase)
  • agents — Lista de agentes activos en este perfil
  • description — Proposito y casos de uso recomendados

Estructura de un ModeProfile

json 
{
  "name": "fast",
  "version": "3.0.0",
  "phases": ["orchestrator", "apply", "verify"],
  "effort": "low",
  "model_strategy": "single",
  "primary_model": "opencode-go/kimi-k2.6",
  "agents": ["ryou-orchestrator", "builder", "reviewer"],
  "description": "CRUDs, simple UI, APIs. Minima sobrecarga.",
  "max_steps": 120
}

exploreExplora el codebase, identifica dependencias y riesgosarchitectGLM-5.1
proposePropone soluciones, evalua tradeoffs y presenta opcionesarchitectGLM-5.1

Niveles de Esfuerzo

Los niveles de esfuerzo controlan la profundidad y cantidad de pasos que cada agente ejecuta:

NivelDescripcionMax StepsUso Tipico
lowIteracion rapida, minimo contexto~120Prototipos, CRUDs, fixes simples
mediumBalance entre velocidad y profundidad~240Features estandar, UI components
highAnalisis profundo, multiples iteraciones~480Arquitectura, refactorizacion legacy
extremeMaxima rigurosidad, revision exhaustiva~800Sistemas mission-critical, compliance

El nivel de esfuerzo se configura en cada ModeProfile y afecta:

  • Numero maximo de pasos por agente
  • Profundidad de exploracion en fase explore
  • Cantidad de alternativas en fase propose
  • Rigor de revision en fase verify

Estrategias de Modelo

REASP soporta dos estrategias de asignacion de modelos:

Single Model

Un unico modelo de IA maneja todas las fases. Ideal para tareas simples donde el overhead de cambio de modelo no justifica el beneficio.

json 
{
  "model_strategy": "single",
  "primary_model": "opencode-go/kimi-k2.6"
}

Per-Phase Model

Cada fase usa el modelo optimo para su proposito. Mayor calidad pero mas overhead de contexto. Recomendado para tareas complejas.

json 
{
  "model_strategy": "per-phase",
  "phase_models": {
    "orchestrator": "opencode-go/glm-5.1",
    "apply": "opencode-go/kimi-k2.6",
    "verify": "opencode-go/deepseek-v4-pro"
  }
}

Soporte Multi-Proveedor

El tool sdd_mode_profile acepta el argumento opcional provider para validar que el modelo pertenezca a un proveedor especifico. 4 providers preconfigurados + opcion de custom models.

Providers preconfigurados

bash 
$ sdd_mode_profile(action="list")

Providers disponibles:
  - opencode-go    (6 models)  [preseleccionado]
    Models: GLM-5.1, Kimi K2.7 Code, DeepSeek V4 Pro, ...
  - anthropic      (3 models)
    Models: claude-sonnet-4-5, claude-opus-4, claude-haiku-4-5
  - openai         (3 models)
    Models: gpt-5, gpt-5-mini, o3-pro
  - google         (2 models)
    Models: gemini-2.5-pro, gemini-2.5-flash

Uso del argumento provider

Cuando se especifica provider, el tool valida que el modelo pertenezca a ese proveedor. Si no coincide, retorna error.

bash 
# Forzar provider especifico (valida que el primary pertenezca al provider)
$ sdd_mode_profile(action="create", name="fast-test",
    primary="opencode-go/kimi-k2.6",
    provider="opencode-go")
> OK, no warning

# Mismatch → rechazado
$ sdd_mode_profile(action="create", name="bad",
    primary="anthropic/claude-sonnet-4-5",
    provider="opencode-go")
> Error: Primary model 'anthropic/claude-sonnet-4-5' does not belong to provider 'opencode-go'

Custom models

Para providers beta o modelos nuevos no listados, REASP acepta el modelo con un warning (no error).

bash 
# Custom model → warning, no error
$ sdd_mode_profile(action="create", name="experimental",
    primary="opencode-go/experimental-v1",
    provider="opencode-go")
> OK, warning: "Model 'experimental-v1' not in catalog of 'opencode-go' (custom)"

Compatibilidad

El argumento provider es opcional. ModeProfiles existentes sin provider siguen funcionando identico (backward-compatible).

REFI v2 · Epic + PART

Metodologia de planificacion empresarial con Epic (subsistema) y PART (15 secciones + 8 quality gates). Workflow de 3 pasadas con 2 STOP gates que esperan confirmacion del usuario antes de codigo.

Workflow de 3 pasadas (con 2 STOP gates)

bash 
Ryou EFI Planner
  |
  +-- Pass 1: Epic Breakdown
  |   +-- request.md
  |   +-- master-blueprint.md
  |   +-- epics/matrix.md
  |   +-- epics/<epic>/README.md
  |        \-> STOP · WAIT FOR USER ·   <-- Gate A
  |
  +-- Pass 2: PART Detail (per EPIC)
  |   +-- epics/<epic>/parts/PARTnn.md (15 sec + 8 gates)
  |        \-> STOP · entre EPICs ·   <-- Gate B
  |
  +-- Pass 3: Orchestration & Hand-off
      +-- orchestration-map.md
      +-- progress.md
      +-- verification.md
       \-> HANDOFF TO ORCHESTRATOR

Las 8 quality gates

#Quality GateFuncion
1Architecture ReviewDiseno vs invariantes / ADRs del proyecto.
2Scope & Completeness AuditTabla declared vs actual, gaps clasificados.
3UX/Design ReviewMeridianUI si UI; contratos si no UI.
4Manual / Runtime ValidationChecklist ejecutado con tickboxes.
5Defect ClosureDefectos de gates 1-4 cerrados en el mismo PART.
6Technical DocumentationDocs tecnicos producidos.
7User DocumentationDocs de usuario producidos.
8Final Review & Sign-offBuild 0/0 + suite verde + Acceptance Criteria re-leido + firma.

Estructura de un PART

Cada PART tiene 15 secciones obligatorias:

  1. Purpose
  2. Current State
  3. Comparison against baseline
  4. Missing / Required Scope
  5. UX Problems
  6. Backend / Logic Problems
  7. Frontend / Presentation Problems
  8. Technical Debt
  9. Required Improvements (verbo + objeto + medida)
  10. Implementation Plan
  11. Automated Test Plan
  12. Manual Validation Checklist
  13. Technical Documentation
  14. User Documentation
  15. Acceptance Criteria (testable)

Cada PART termina con un footer de 8 casillas verificables (una por quality gate) que se firman en orden estricto antes de cerrar el PART.

Anti-hallucination block

Las secciones §3 (Comparison), §9 (Required Improvements), §10 (Implementation Plan), y §15 (Acceptance Criteria) tienen reglas anti-alucinacion que prohiben inventar archivos, endpoints, columnas, o criterios subjetivos.

Backward-compatible

Los 4 paquetes legacy (reasp-backup-manager, linux-compat, multi-agent-compatibility, sdd-profile-provider-support) siguen funcionando con REFI v2. El flag epic_part.legacy_domain_shards_fallback: true los acepta sin tocarlos.

Slash Commands

Comandos integrados en OpenCode Go para gestionar REASP sin salir del editor.

/sdd — ModeProfile Manager

Gestiona ModeProfiles: lista, cambia, crea, edita y elimina perfiles.

opencode 
/sdd list              # Lista todos los ModeProfiles
/sdd switch fast       # Cambia a perfil Fast
/sdd create mymode     # Crea nuevo ModeProfile
/sdd edit fast         # Edita perfil Fast
/sdd delete oldmode    # Elimina perfil

/sdd-mode / /sm — Quick Mode Switch

Cambia rapidamente de ModeProfile sin menu interactivo.

opencode 
/sdd-mode fast
/sm ui
/sm enterprise

/sdd-profile / /sp — Quick Profile Switch

Alias alternativo para cambio rapido de perfil.

opencode 
/sdd-profile architecture
/sp debug

/rass-setup / /reasp-setup — Setup & Status

Muestra estado, despliega agentes o verifica configuracion. /reasp-setup permite cambiar entre el flujo de planificacion EFI y el de implementacion.

opencode 
/rass-setup status     # Estado actual de REASP
/rass-setup deploy     # Despliega agentes a config
/rass-setup check      # Verifica configuracion
/rs

AI Tools

Herramientas programaticas que los agentes pueden invocar para gestionar REASP desde codigo.

sdd_mode_profile

Gestiona ModeProfiles programaticamente.

python 
# Listar perfiles
sdd_mode_profile(action="list")

# Cambiar de perfil
sdd_mode_profile(action="switch", name="fast")

# Crear perfil custom
sdd_mode_profile(
    action="create",
    name="my-custom",
    phases="orchestrator,apply,verify",
    effort="low",
    model_strategy="single",
    primary="opencode-go/kimi-k2.6"
)

# Obtener estado actual
sdd_mode_profile(action="status")

rass_setup

Gestiona la configuracion de agentes y estado de REASP.

python 
# Ver estado completo
rass_setup(action="status")

# Desplegar agentes a configuracion
rass_setup(action="deploy")

# Verificar que agentes estan configurados
rass_setup(action="check")

reasp_setup

Gestiona el flujo de trabajo REASP, permitiendo cambiar entre el Ryou EFI Planner y el Ryou Orchestrator, y alternar la funcionalidad REFI.

python 
reasp_setup(action='switch-workflow', workflow='ryou-efi-planner')
reasp_setup(action='toggle-feature', feature='refi', enabled=True)

Ryou EFI Planner

Orchestrator

El Orchestrator es el cerebro de REASP. Recibe la solicitud del usuario, analiza la complejidad y decide que ModeProfile y agentes activar.

PropiedadValor

markdown 
# Ryou Orchestrator v3.0.0

- Siempre delega al builder para implementacion

- Si la tarea es UI pura, usa ModeProfile UI

    "design": "opencode-go/glm-5.1",
    "apply": "opencode-go/kimi-k2.6",

  },
  "agents": ["ryou-orchestrator", "architect", "builder", "reviewer"],
  "description": "Desarrollo de APIs REST con diseno de contratos",
  "max_steps": 240,
  "custom_rules": ["api-rest", "openapi-3"]
}

cp api-dev.json .opencode/sdd-profiles/

Reglas Globales

Las reglas globales aplican a todos los agentes. Se encuentran en .opencode/rules/.

Archivos de Reglas

  • global-rules.md — Convenciones de codigo, estilo, patrones prohibidos
  • meridianui.md — Reglas especificas del design system MeridianUI

Ejemplo de global-rules.md

markdown 
# Global Rules v3.0.0

## Codigo
- Usar C# 12 features cuando apliquen
- Preferir async/await sobre .Result o .Wait()
- Propagar CancellationToken cuando sea natural
- Validar inputs en los boundaries

## Arquitectura
- Preservar direccion de dependencias
- Domain no depende de Infrastructure
- Usar IQueryable hasta materializacion
- AsNoTracking() para lecturas

## Prohibido
- Hardcodear secrets
- async void (excepto event handlers)
- Prematuro ToList()
- N+1 queries

FAQ

Que diferencia a REASP de otros frameworks de IA?

REASP es el unico framework que adapta dinamicamente el pipeline segun la complejidad. Otros usan un flujo fijo de 5-8 fases para todo. REASP usa 3 fases para un CRUD y 8 para un sistema enterprise. Eso se traduce en menos tokens, menos tiempo y menos frustracion.

Puedo usar REASP sin OpenCode?

REASP esta disenado como plugin de OpenCode, pero funciona con cualquier modelo conectado a OpenCode, incluyendo modelos locales via LM Studio u Ollama. La integracion con el sistema de agentes de OpenCode es parte de su valor.

Es REASP open source?

Si. REASP es Open Source bajo MIT License. Puedes clonarlo, modificarlo y contribuir. El codigo esta disponible en GitHub.

Puedo crear mis propios ModeProfiles?

Si. Crea un archivo JSON en .opencode/sdd-profiles/ y usalo con /sdd switch mi-perfil. Ver la seccion Crear ModeProfile Custom.

Que pasa si un agente falla?

El orchestrator detecta el fallo y puede: (1) reintentar con el mismo agente, (2) delegar a un agente alternativo (ej: debugger para un builder fallido), o (3) escalar al usuario con un resumen del problema.

Puedo desactivar agentes que no necesito?

Si. Edita el ModeProfile activo y remueve agentes del array agents. O usa el TUI installer para desactivarlos globalmente.

Como actualizo REASP a una nueva version?

bash 
cd REASP
git pull origin main
cd installer
npm install
node index.js --update

REASP funciona offline?

Parcialmente. Los ModeProfiles Architecture y Enterprise estan disenados para generar especificaciones completas offline que puedes implementar despues. Pero la ejecucion de agentes requiere conectividad a los modelos de IA.

Cuanto cuesta usar REASP?

Gratis. REASP es Open Source bajo MIT License. Solo pagas por los tokens de IA que uses con tus proveedores (OpenAI, Anthropic, Gemini, etc.) o si usas modelos locales, no hay costo adicional.

Troubleshooting

Instalacion duplicada en PATH (Windows)

Sintoma: reasp --version retorna la version antigua. Las funciones nuevas no aparecen tras actualizar el tarball.

Causa: 3 instalaciones simultaneas posibles en Windows:

  • C:\Program Files\REASP\ — instalacion antigua con prioridad alta en PATH.
  • %APPDATA%\npm\node_modules\reasp-cli — instalacion npm global correcta.
  • ~\KeorSoft\Development\AITools\REASP — repo de desarrollo.

Solucion A — Sincronizar manualmente (como admin):

powershell 
robocopy "C:\Users\kevin\KeorSoft\Development\AITools\REASP" `
         "C:\Program Files\REASP" `
         /MIR /XD .git node_modules installer\node_modules

Solucion B — Eliminar (como admin):

powershell 
Remove-Item -LiteralPath "C:\Program Files\REASP" -Recurse -Force

Despues de cualquier opcion, regenera y reinstala:

bash 
npm pack && npm install -g reasp-cli-1.0.1.tgz

Proveedores no aparecen en el selector del TUI

Sintoma: Al configurar un ModeProfile, el selector de proveedores muestra una lista vacia o solo opencode-go.

Causa: api.state.provider no se inicializa correctamente. Esto ocurre con versiones de OpenCode anteriores a 1.17.17.

Solucion:

  1. Verificar version de OpenCode: opencode --version (debe ser 1.17.17 o superior).
  2. Si es inferior, actualizar: npm install -g opencode@latest.
  3. Reinstalar REASP: npm install -g reasp-cli.

Error: "ModeProfile not found"

Sintoma: Al ejecutar reasp switch my-profile, retorna "ModeProfile not found" aunque el perfil existe en el repo.

Causa: Hash mismatch entre el repo (REASP/.opencode/) y el plugin instalado (~/.config/opencode/).

Solucion — Sincronizar manualmente:

bash 
node scripts/sync-reasp.js push

Esto copia .opencode/ → ~/.config/opencode/ y refresca el runtime desde el ModeProfile activo.

Error: "ModeProfile not found" (sintaxis JSON)

Causa: El archivo JSON del ModeProfile no existe o tiene errores de sintaxis.

Solucion:

bash 
# Verificar que el archivo existe
ls .opencode/sdd-profiles/

# Validar JSON
node -e "JSON.parse(require('fs').readFileSync('.opencode/sdd-profiles/fast.json'))"

# Resetear a default
/sdd switch ryouset

Error: "Agent not configured"

Causa: El prompt del agente no se desplego correctamente.

Solucion:

bash 
/rass-setup deploy
/rass-setup check

Error: "Model not available"

Causa: OpenCode Go no tiene acceso al modelo especificado en el ModeProfile.

Solucion:

  • Verifica que tienes creditos/API keys configuradas en OpenCode
  • Cambia el modelo en el ModeProfile a uno disponible
  • Usa model_strategy: "single" con un modelo que si tengas disponible

Performance lenta en fase "explore"

Causa: Proyectos grandes con muchos archivos.

Solucion:

  • Usa ModeProfile Fast para tareas localizadas
  • Reduce el scope en la solicitud (menciona archivos especificos)
  • Aumenta max_steps si el agente necesita mas tiempo

El builder genera codigo que no compila

Causa: Contexto insuficiente o reglas globales no cargadas.

Solucion:

  • Verifica que .opencode/rules/global-rules.md existe y es valido
  • Proporciona mas contexto en la solicitud (interfaces existentes, DTOs)
  • Usa /rass-setup check para verificar estado
